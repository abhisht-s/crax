# Craxii V0.0.1 — Final Product Decisions and System Architecture

**Decision record:** 12 October 2026  
**Status:** Approved architecture and product direction; explicitly identified policy and integration details remain open  
**Scope:** What V0.0.1 is, how its components relate, the decisions made, their rationale, and the boundaries of the release. **This document is not an implementation plan and does not define stages or build order.**

## 1. Product definition and release objective

Craxii is a persistent AI agent with its own computer. A person communicates with Craxii through Telegram, assigns it real work, and expects it to reason, use tools, run commands, inspect or change files, work in repositories, and report results. Its computer is a real Linux environment rather than a simulated tool interface. Craxii preserves its conversations, execution records, workspaces, and files so that it can resume after process interruptions, restarts, and periods when its machine is switched off. The model is a replaceable inference provider; the persistent agent, its environment, execution discipline, identity, and recoverable state together form Craxii.

The V0.0.1 objective is a **fully self-service, sellable consumer prototype**. An unfamiliar customer must be able to visit the website, create an account, begin a seven-day trial without supplying a payment method, link Telegram, have their own AWS computer provisioned automatically, message their agent, see it complete work, and return later to find their state intact. When the trial expires or its allowance is consumed, the customer can explicitly pay to continue with the same logical Craxii. Ordinary signup, trial activation, machine creation, communication, sleep, wake, and paid conversion must not require founder intervention. Exceptional incidents may be handled by an operator using documented procedures, provided the customer’s state and paid entitlement are not silently lost.

V0.0.1 is deliberately not a complete autonomous fleet-management platform. Our priority is getting a reliable, secure, compelling product into customers’ hands quickly, while measuring actual usage and validating willingness to pay. The project will preserve existing working V0.0.01 capabilities instead of rebuilding its agent internals unnecessarily.

## 2. Overall separation of responsibilities

The system has three logical parts: the **client layer**, the **Craxii Universal Backend**, and the **customer-machine universe**. The client layer consists of the public website and Telegram. The website provides identity, trial activation, billing, account controls, Telegram linking, remaining allowances, and machine status. Telegram is the primary place where the customer instructs Craxii and receives answers. Neither interface performs agent reasoning or directly manages cloud resources.

The Universal Backend is the always-running control plane. It owns canonical customer identity mappings, access entitlements, billing-state interpretation, durable Telegram ingress and delivery, customer-to-machine ownership, machine provisioning, authenticated worker communication, worker readiness, background operation records, sleep and wake decisions, usage accounting, model-call authorization, backups, and minimum operational visibility. The backend **does not execute customer agent loops or customer shell tools**. It may proxy model requests as a security and spending boundary; forwarding an inference request is distinct from hosting the reasoning loop.

The customer-machine universe consists exclusively of **AWS EC2** instances in V0.0.1. Every customer has one dedicated Linux VM and dedicated persistent EBS data disk. The existing Rust Craxii runtime runs in that VM, maintains the canonical local agent SQLite state and files, and carries out model-driven tool execution. Machines initiate secure outbound connections to the Universal Backend. They have no reason to receive the Telegram bot token, central PostgreSQL credentials, Razorpay administrator keys, customer account tokens, or fleet-wide AWS permissions.

## 3. Repository and source ownership

We chose **Option C: three separate repositories** after a read-only Codex audit of the actual Rust codebase and comparable real-world systems. The existing public **`craxii`** repository remains the source of the Rust agent runtime. The new **`craxii-control-plane`** repository is **private** and owns the Universal Backend. The existing **`craxii_website`** repository continues to own the Next.js website. The fact that the Universal Backend is privately sourced is a deliberate source-ownership and commercial decision, not a substitute for secure authentication, authorization, secret storage, and infrastructure isolation.

The public Rust runtime and private backend communicate through a small, language-neutral, independently versioned worker contract, with JSON Schema and documented message semantics as the selected starting approach. The agent and backend are separate release artifacts with separate deployment permissions and timelines. A source change that compiles successfully against a current agent does not prove compatibility with an old machine that has slept for weeks. The backend must therefore recognize the capabilities and protocol versions still present in the installed fleet; older protocol handlers cannot be removed while supported installations may reconnect using them. Tests must exercise released older worker behavior rather than testing only the latest source on both sides.

The current Stage 27 V0.0.01 installation remains untouched as a reference. The first V0.0.1 owner canary must be a **new machine provisioned by the same automated mechanism intended for customers**, without silently adopting the existing instance or data disk.

## 4. Universal Backend language and application structure

The Universal Backend will be written in **TypeScript on Node.js**, rather than Rust or Go. The main driver was engineering throughput: the backend’s dominant work is database, webhook, cloud-API, and network coordination, and faster Codex iteration matters more at this stage than the potential CPU and memory advantages of Go or Rust. The existing agent runtime stays in Rust. The website remains in TypeScript/Next.js. The language difference is intentional and makes an explicit wire contract essential.

The backend remains **one logical application**, with appropriately separated internal modules and long-running background work. This does not require microservices, a separate job broker, Kubernetes, or a distributed workflow platform. Its durable authority lives in PostgreSQL, not in process memory. Internal concurrency must be bounded; repeated cloud actions and messages must be idempotent or reconciled. TypeScript static types are not considered sufficient validation of untrusted network data, so authentication and runtime validation are mandatory at public and worker interfaces. The exact HTTP framework, ORM/query builder, migration runner, and job-loop library are **engineering selections not yet ratified as product decisions**.

## 5. Central compute and deployments

The Universal Backend is hosted in **AWS Mumbai (`ap-south-1`)** on a dedicated **EC2 `t3.small`**, initially 2 vCPUs and 2 GiB RAM. It runs as a **Dockerized Node.js application**. The private repository is the source; the released artifact is a built image, not a Git checkout casually executed on the production host. **GitHub Actions** is the planned deployment automation and **Amazon Elastic Container Registry (ECR)** stores approved images. Secrets must never be baked into those images or committed to the repository. Backend configuration and privileged cloud access are supplied through restricted runtime mechanisms.

One backend EC2 instance is the accepted V0.0.1 availability posture. Docker offers reproducible packaging and controlled application-image deployment, but does not make a single server highly available. EC2 host failure can interrupt API availability until the machine is recovered. The selected instance size is an initial operating hypothesis and can be increased based on observed memory, CPU-credit behavior, request latency, and background-job delays; it is not a verified capacity guarantee.

We are **not** introducing ECS, Kubernetes, AWS Lambda, Azure Functions, or Cloudflare Workers for this release. Those services would add deployment and operational surfaces without a demonstrated first-release requirement.

## 6. Central PostgreSQL and database management

The Universal Backend uses **Amazon RDS for PostgreSQL**, initially **`db.t4g.small`** with 2 vCPUs and 2 GiB RAM in `ap-south-1`. The initial deployment is **Single-AZ** with approximately 20 GiB of supported general-purpose SSD storage, encryption at rest, private networking, deletion protection, **seven days of automated backups**, and point-in-time recovery. RDS manages much of the underlying database infrastructure; Craxii still owns schema design, query correctness, access control, migrations, backup configuration, monitoring, and restore tests. The chosen Single-AZ design consciously accepts possible database downtime during certain failures or instance-size changes.

Central PostgreSQL is the durable source of truth for customer records, external authentication identifiers, contact and consent data, trial status, subscriptions, payment-event evidence, entitlements, machine ownership, AWS resource IDs, provisioning obligations, worker identity and generation, machine lifecycle status, queued Telegram obligations, response-delivery records, compute and model budget accounting, and backup inventories. It is **not** the long-term canonical filesystem or complete execution journal for every customer agent. Those remain on each customer’s persistent EBS disk and local SQLite database.

Schema changes are versioned SQL migrations tested locally before a controlled production application. The earlier SQLx CLI recommendation related to the former Rust-control-plane plan; **SQLx has not been chosen for the new TypeScript control plane**. The migration tool should be chosen to support reliable forward-compatible PostgreSQL changes, transaction and schema-version tracking, and a deployment process that does not break the running application. For visual database inspection, DBeaver can connect over an authorized private management path; RDS does not provide a Supabase-style built-in graphical table editor.

RDS will **not be publicly accessible**. Its PostgreSQL security group allows access on port 5432 only from the authorized backend security group. Connections require TLS with server-certificate and hostname validation. Normal application access uses a least-privilege PostgreSQL role distinct from migration and administrator roles. Database credentials are managed securely, with AWS Secrets Manager selected for central application secrets. Neither customers nor customer VMs receive RDS connectivity or credentials. Parameterized queries and ownership checks remain necessary even with private networking.

## 7. Website, domains, DNS, and public ingress

The existing **`craxii.com`** Next.js site remains a **static deployment on Cloudflare**. We are not adding a separate always-running Next.js server merely to handle authentication, billing, or account operations; those operations use the Universal Backend’s authenticated APIs. The browser authenticates with Cognito and supplies a valid token to the backend, which validates identity and performs customer-specific authorization. Protected-looking frontend controls do not themselves enforce access restrictions. Browser token handling, CORS, and sensitive actions must be designed accordingly.

The Universal Backend’s planned public hostname is **`api.craxii.com`**. The selected ingress chain is **Cloudflare Free → Caddy HTTPS reverse proxy → Dockerized TypeScript backend**. One API hostname can expose separately secured customer APIs, Telegram/Razorpay webhook routes, and worker communication routes. The backend application port is not published directly. The anticipated incremental Cloudflare subscription cost is **$0**, using the existing zone and included Free features. There is no V0.0.1 requirement for a paid Cloudflare tier, AWS Application Load Balancer, or Cloudflare Workers.

Cloudflare does not replace route-specific authentication or application-level rate limits. Caddy/origin TLS, direct-origin bypass protection, and real behavior of long-lived worker connections must be checked. If proxy timeouts interfere with authenticated worker connections, the worker route may require a different connection arrangement without changing the settled website/API ownership. We have not finalized a particular WebSocket-versus-long-polling transport solely by selecting HTTPS authentication.

## 8. Customer authentication and account ownership

We selected **Amazon Cognito Essentials** instead of Clerk or Microsoft Entra External ID for the customer-facing authentication service. Supported initial login methods are **email/password and Google sign-in**. Cognito handles password authentication, sign-in flows, recovery, and identity-token issuance. The website can use an OAuth Authorization Code flow with PKCE; the backend verifies token issuer, signature, audience/client binding, lifetime, and relevant claims before mapping to a Craxii customer record.

Craxii’s PostgreSQL record is the canonical business customer and connects the stable Cognito subject to subscription entitlements, mandatory submitted phone information, legal consent, Telegram numeric identity, and machine ownership. An email address is not used as the unique durable authorization identity. A customer’s Telegram user is linked through an authenticated, one-time linking flow; Telegram usernames are never used as authoritative identity. Worker identity is separate again and is not a Cognito customer session. The precise phone-verification and repeat-trial policy remains open; the required phone field does not, by itself, prove a unique person.

## 9. Subscription, pricing, and commercial access

The initial advertised subscription is **US$49 per month**. It includes a **US$20 per paid billing period hard cap on model API expenditure** and **180 cumulative EC2 running hours per paid billing period**, with **no automatic usage overages**. The earlier phrase “six hours per day” describes the allowance’s average, **not a separate daily cutoff**: an eligible customer may use more than six hours on one day while staying within the 180-hour monthly cap. The period follows the paid subscription billing window rather than an unspecified calendar month. The account, files, and logical Craxii continue across renewals; allowances are reset by verified new paid periods, not by repeated webhooks or application restarts. Rollover of unused allowances has not been approved and is not promised.

A **seven-calendar-day free trial** is a core V0.0.1 feature, not a later experiment. The customer **does not supply a payment method upfront**. The trial includes a real dedicated AWS computer and the normal core agent capabilities but is bounded by a **total US$5 model budget** and **12 cumulative EC2 running hours**. The trial ceases to admit chargeable work at whichever occurs first: the seven-day end, model-budget exhaustion, or running-hour exhaustion. Existing state is preserved. There is no automatic conversion or charge at day seven; continuing requires an explicit, verified US$49 subscription. Trial-to-paid conversion should preserve the customer’s existing logical Craxii, files, and state rather than silently replacing them with an empty agent.

For both paid and trial allowances, limits are centrally durable and enforced, including across restarts and concurrent operations. The system must not begin new chargeable work without entitlement and sufficient reserved budget. When limits are approached during active work, it should safely checkpoint, pause, or complete bounded already-admitted work as policy allows without corrupting SQLite, files, or execution state. Exact reservation/grace mechanics and how running hours are measured at cloud lifecycle boundaries are implementation contracts to verify, not excuses to silently exceed the promised caps.

## 10. Payment provider and billing authority

**Razorpay** is the approved V0.0.1 payment gateway. We considered Stripe’s startup benefits but decided not to delay the product waiting for Stripe India eligibility or discount confirmation. Razorpay will process authorized checkout and subscriptions where supported; **the Craxii backend decides access rights from verified payment evidence**. Its internal subscription and entitlement model should not consist of Razorpay-specific objects, so a later gateway change does not require redesigning machine ownership or agent state. Switching payment integrations is manageable; migrating active recurring mandates may still require new customer authorization.

The intended customer-facing price is **US$49**, including international customers. What remains to be confirmed externally is whether this specific India-based merchant account is authorized for the required USD recurring transactions, supported countries and payment methods, settlement currency, fees, invoicing, and relevant tax handling. Generic documentation about Razorpay capabilities is not proof of activation on this merchant account. Before taking live subscriptions, we must exercise supported flows in test mode and validate live merchant eligibility with Razorpay.

A verified first payment creates or extends the customer’s paid entitlement; an unverified or failed payment must not grant paid access. The backend must treat payment collection, entitlement, and cloud provisioning as distinct durable facts. A successful payment followed by slow provisioning leaves a recoverable obligation rather than an invitation to pay twice. After a reasonable delay, the customer should see accurate pending/support status rather than an invented “ready” machine.

Duplicate, delayed, or out-of-order Razorpay notifications must not double-provision machines, double-reset budgets, or extend subscriptions more than once for the same billable period. Payment-provider callbacks require signature verification and durable idempotency, with reconciliation when events or provider observations disagree. A successful monthly renewal extends access and resets the allowance for the new entitled period. Failed renewal does not erase already-paid access; once that paid period ends, **no additional chargeable work or wake-ups are authorized**, and no free compute grace period is intended. Cancellation disables future renewal while leaving access available through the already-paid period unless the customer affirmatively requests earlier closure. The same customer can reactivate within retention without losing their history.

The complete business policy for **refund eligibility, refund deadlines, discretionary dissatisfaction refunds, duplicate captures, chargebacks, disputes, payment reversals, and the exact published customer terms is not yet finalized**. The default technical safety requirement is that an unfulfilled paid activation has a clear support/refund resolution path, and a reversal must never cause unauthorized further spending. These cases need explicit, tested state transitions and truthful customer notices before accepting production payments. They are not automatically solved by selecting Razorpay.

## 11. Trial abuse, account checks, and resource control

Because a trial requires no card and consumes real machine and model resources, V0.0.1 must prevent trivial repeat signups and automated infrastructure abuse. The agreed direction is one normal trial per legitimate customer, supported by authenticated identity, required contact information, bounded activation rates, usage caps, and fraud signals. The exact identity-verification requirement, duplicate-account criteria, trial-reset exception policy, and escalation threshold are **not yet finalized**. Neither a Google account nor a submitted phone number inherently guarantees one trial per physical person. Abuse controls should be strong enough to protect spending without demanding unnecessary sensitive personal documentation from ordinary customers.

Cloud compute and model budgets are separately enforced. A trial can use at most 12 EC2 running hours and US$5 of model inference; a paid period can use at most 180 EC2 running hours and US$20 of model inference. The backend must track actual cloud power states and reconcile its ledger after crashes or missed lifecycle observations. The 30-minute safe-idle shutdown reduces waste but does not replace the explicit running-hour cap. Compute-hour rates and hard caps do not include or eliminate recurring EBS, snapshot, public IPv4, or other infrastructure charges while machines are stopped.

## 12. AWS-only customer workstations

**All V0.0.1 customer compute is on AWS.** This supersedes the former plan for alternating AWS and Azure VMs, provider placement, Azure worker resource groups, Azure worker NAT, Azure VM images, and cross-cloud provisioning. Azure remains part of the product solely as the primary model-inference provider. Accordingly, there is no V0.0.1 requirement for a cross-cloud customer placement engine or an AWS-to-Azure federation identity just to provision customer VMs.

Each AWS customer installation starts from an approved **Ubuntu 24.04 LTS x86-64** image and runs on **EC2 `t3.large`**, with 2 vCPUs and 8 GiB RAM. The base configuration includes an approximately **30 GiB encrypted, rebuildable OS disk** and a separately created **80 GiB encrypted gp3 EBS data volume**, mounted at **`/srv/craxii-data`** using ext4. The agent’s canonical SQLite state, execution records, conversations, files, home data, and workspaces live on the data volume. The existing paths `/var/lib/craxii`, `/srv/craxii/workspaces`, and `/home/craxii` must resolve to that persistent storage, consistent with the tested Stage 27 conceptual layout.

The operating-system image contains a pinned, prebuilt Rust agent release and needed trusted/system utilities. We do not clone the public repository and compile the agent for every signup. A versioned, secret-free AMI makes provisioning faster and more reproducible. Per-customer boot configuration must contain no permanent fleet secret. The existing fixed launcher and split between a privileged/trusted worker service and an unprivileged model-controlled `craxii` Unix user are preserved and reverified in the new AMI.

## 13. Automatic AWS provisioning and durable ownership

The TypeScript backend will use the **official AWS SDK for JavaScript v3** to create and manage approved EC2 customer resources. A valid trial or paid entitlement creates a **durable, unique provisioning obligation** in PostgreSQL. Before the first external cloud write, the backend commits an immutable installation identity, target region/Availability Zone, approved AMI and instance shape, expected storage configuration, and stable operation identifiers. This prevents a lost API response from causing an uncontrolled second allocation or placement drift. Since AWS is the only VM provider, the prior round-robin placement/fallback policy is no longer part of the release.

The backend creates the intended encrypted data volume in the selected Availability Zone, launches a machine with exact approved settings, attaches the known volume, reconciles the cloud resource identifiers, and waits for guest enrollment and recovered readiness. A cloud operation returning success, an EC2 instance entering `running`, or a successful user-data execution alone does **not** mean Craxii is ready. Readiness requires correct disk identity/mounts, initialized or recovered worker state, an authenticated current worker, and an operational agent service.

Provisioning uses a persisted operation journal, stable AWS client tokens where supported, immutable request fingerprints, deterministic ownership tags, exact resource IDs, and reconciliation against AWS observations after timeouts or backend restarts. The backend may retry genuinely safe operations but must not assume that a network timeout means the AWS action did not happen. EC2 zonal idempotency and EBS attachment-in-the-same-AZ restrictions must be respected. A genuine unresolved mismatch stops automatic provisioning and surfaces a support-needed state rather than risking a second machine or another customer’s disk.

The backend’s EC2 IAM role uses temporary credentials through its instance profile and is limited to approved worker resources and lifecycle actions. Worker instances use a separate, narrow instance profile for operator access where necessary. The normal backend identity does not need permission to edit unrelated IAM roles or security groups, publish arbitrary AMIs, or delete customer disks. Destructive cleanup initially belongs to a separately authorized operator. Resource tags support reconciliation and limited permission checks but do not by themselves prove customer ownership; the backend must validate its durable database mapping and exact provider resource IDs.

## 14. Worker networking and cloud access

V0.0.1 accepts the audited AWS networking approach of **auto-assigned public IPv4 on customer workers for outbound internet access**, combined with a **security group that has no inbound rules**. This avoids a fixed-cost shared NAT Gateway for the small initial cohort. A public address with blocked inbound traffic is not identical to having no public address, so the configuration must be inspected and tested. No public SSH listener or open inbound management service is part of the intended product. The machine initiates its connection to `api.craxii.com` and may use the internet for authorized agent tasks.

Operator access uses **AWS Systems Manager Session Manager** with the minimum instance profile and authorized human permissions. The model-controlled shell must not be able to obtain the worker’s instance-profile credentials through EC2 metadata. **IMDSv2 is required but is not sufficient by itself**: host-level restrictions must deny metadata access to the model execution identity. Workers must also be unable to reach the central RDS database or obtain Secrets Manager, Razorpay, Cognito administrative, or fleet-control credentials.

## 15. Secure worker enrollment and communication

The selected machine-authentication design is **HTTPS with Ed25519 machine keys, one-time enrollment, signed challenges, short-lived authenticated sessions, and central lifecycle-generation fencing**. We explicitly decided not to operate a private mTLS certificate authority for V0.0.1. The protocol is separate from the existing V0.0.01 native-client HTTP/WebSocket protocol and must remain language-neutral between TypeScript and Rust.

A new worker receives a short-lived, single-use enrollment credential tied to the backend’s expected installation and cloud resource. Its trusted process generates an asymmetric keypair and protects the private key from the model-controlled shell. The backend checks enrollment eligibility and suitable cloud identity evidence, verifies possession of the private key, consumes the enrollment credential at most once, and binds the public key to the current installation and generation. Subsequent sessions renew through a fresh signed challenge over verified TLS rather than requiring a long-lived bearer credential in an AI-accessible file.

Every authority-bearing operation validates the authenticated worker, customer/installation mapping, current generation, permitted message scope, and applicable entitlement. A machine replaced or explicitly revoked loses authority even if it reconnects with an old key. Enrollment challenges must be fresh, short-lived, and replay-resistant. Session credentials must be bounded and protected; sensitive operations should not rely on an indefinitely reusable stolen bearer token. Sleeping machines can reauthenticate after weeks offline. Reusing HTTPS connections and sessions should keep authentication overhead insignificant relative to model and VM-wake latency; this must be measured, not merely asserted.

## 16. Durable message and response lifecycle

One **shared Telegram bot** belongs to the Universal Backend, not one bot per customer VM. A customer links their numeric Telegram account through a controlled one-time flow backed by their logged-in Craxii account. On receiving an authorized message, the backend durably records the inbound envelope and its deduplication identity before trying to wake or deliver to a worker. A stopped machine’s queued work remains in the central database until the worker can safely receive it.

The worker must admit each canonical envelope **once** into its own SQLite-backed durable agent work queue, and it acknowledges acceptance only after the local transaction has committed. Lost acknowledgements can be retried because the worker retains the message ID/digest receipt. Once execution finishes, the worker commits its result locally and exports it with a stable identifier; the backend accepts that export idempotently and handles final Telegram delivery. The delivery path distinguishes work admission, work execution, result export, and channel send as different durable events. An ambiguous Telegram send result must not be blindly retried if that could duplicate a user-visible response. Normal work and recovery remain governed by the existing runtime’s conservative semantics.

The backend maintains enough routed content and metadata for reliable delivery and recovery but does not become the canonical archive of the agent’s entire conversation and filesystem history. It must not send messages or results across customer boundaries merely because a client supplies a different installation ID. The authenticated server-side ownership mapping remains authoritative.

## 17. Sleep, wake, and allowance exhaustion

Customer VMs should **stop after 30 minutes of safe inactivity**, not after 30 minutes without a heartbeat or simply because the user has not sent another message. Safe inactivity requires accounting for active commands, pending results, uncommitted local state, and work that must be safely completed or checkpointed. The control plane records a desired state, coordinates a safe point with the current worker, checks newly queued work, and requests AWS stop only when the race is resolved. New inbound work arriving during sleep is saved first and triggers a coalesced wake, followed by authenticated guest readiness and local-state recovery.

When a trial or paid compute budget is exhausted, the service must stop authorizing new chargeable work and move the VM toward a safe stopped state. It must preserve files, SQLite integrity, and work receipts. If the machine cannot safely reach a stopping point immediately, bounded in-flight behavior needs explicit implementation rules rather than pretending that hard limits and instantaneous shutdown are always compatible. The same distinction applies to model budget reservations and streaming model requests. No automatic paid overages are authorized.

## 18. Azure AI Foundry model inference

**Microsoft Azure AI Foundry is the selected primary LLM provider**, with the existing Azure startup credits intended to fund eligible model calls. The user has stated that their program terms permit the relevant Foundry model usage except Anthropic models. We will benchmark multiple models later; **Kimi K2.5 is a candidate, not the finalized default**. Choosing a model solely by per-token price is insufficient for an agent that may require many tool-use iterations. The performance target is successful work with acceptable latency and total model expense.

The proposed security boundary is a **narrow model-call proxy inside the Universal Backend** rather than a separate V0.0.1 service. The Rust agent’s reasoning loop remains on the customer VM, but its trusted component requests model inference through the backend, which validates machine identity, entitlement, spending budget, model choice, and concurrency. The backend forwards or streams inference requests to Azure while keeping provider-wide model credentials in trusted server-side storage. Model credentials must not be available to the model-controlled shell. This proxy design is the approved architectural direction; detailed request-streaming, spend reservation, disconnection, provider credential mechanism, and model-specific configuration must still be tested during implementation.

All customer VM provisioning and fleet management stays on **AWS**, even though model inference runs on **Azure**. A requirement to use Azure Foundry does not reintroduce Azure VM provisioning or cross-cloud compute placement. The model interface should remain adaptable enough to support another authorized provider later without rewriting Craxii’s agent execution core.

## 19. Data ownership, snapshots, recovery, and retention

Customer information is divided between central operational records in RDS and **canonical agent state on each dedicated EBS data disk**. Agent state includes local SQLite, conversation history, work admission and execution records, remembered context, home-directory contents, repositories, workspaces, downloaded assets, and generated files. The OS disk is disposable and must not silently hold canonical user content. On first initialization, the disk must be matched to the exact expected AWS volume ID and shown to be genuinely blank before formatting. On reboot or machine replacement, the existing ext4 filesystem must be recognized and mounted, **never formatted again**. Missing mounts must prevent trusted agent startup rather than redirecting writes onto the OS root disk.

We agreed to a **one-year retention intention for customer data after cancellation or entitlement expiry**, replacing the earlier 30-day proposal. This is a product obligation, but its most economical and safe storage mechanism has **not** been finally approved. The favored option is to safely stop the machine, create and verify a final encrypted recoverable EBS snapshot, retain a durable snapshot-to-customer mapping, and then remove unnecessary running compute and provisioned volumes. On reactivation, Craxii would reconstruct an EBS disk from the snapshot and preserve the customer’s logical agent state. Whether and when old disks may be deleted must depend on verified snapshot completion and an actual restore test. Snapshots are not automatically guaranteed to be application-consistent for a busy SQLite/filesystem workload.

During active service, the baseline is **daily encrypted off-machine data-disk backups** with safe snapshot coordination. An initial proposal of seven daily and four weekly recovery points exists, but the exact active-customer backup retention schedule is **not yet approved**. RDS backups are independent and retain seven days of PITR. Operator-assisted snapshot restoration and VM replacement are acceptable in V0.0.1, but the backup path must be proven on a fresh disposable installation before paid launch. Valid account/data deletion requests and applicable legal preservation duties may override a blanket one-year retention promise; the exact deletion policy must be approved and implemented clearly.

## 20. Failure handling and operational assurance

The system must preserve the distinction between **verified entitlement**, **provisioning obligation**, **cloud resource created**, **guest initialized**, **worker securely enrolled**, and **agent ready**. These are not interchangeable states. PostgreSQL-backed durable jobs, unique constraints, process-crash recovery, bounded retries, and AWS resource reconciliation are sufficient for V0.0.1; a more sophisticated workflow engine is not required. A backend restart must not lose a paid obligation, duplicate a VM, or authorize extra monthly usage. Ambiguous provider outcomes are reconciled through stable IDs and observed resources before any additional creation call.

The customer should receive truthful activation and operational status, including when a worker is provisioning, sleeping, waking, delayed, degraded, or needs support. A slow provisioning operation must not solicit a second payment as a remedy. Exceptional cloud recovery, deletion, and support may be operator-driven, provided ownership is validated and customer data is preserved. Minimal structured logging, a small operator interface/CLI, and alerts for failed provisioning, backup failures, unusual spend, resource quota exhaustion, and loss of the backend or database are needed; a full monitoring dashboard and fully automated recovery system are not V0.0.1 requirements.

The early hosting design uses one backend instance and Single-AZ RDS. This is an explicit cost and complexity tradeoff, not a claim of high availability. It means recovery procedures and customer-status accuracy matter. Exact regional prices, provisioned quotas, effective IAM permissions, certificate/session implementation, worker AMI behavior, Cloudflare connection durability, and true per-customer bills require live acceptance evidence before commercial launch.

## 21. Scope exclusions and superseded decisions

The earlier **AWS/Azure alternating customer-VM policy is superseded**. All V0.0.1 customer VMs run on AWS; Azure serves inference. Consequently, Azure VM images, Azure worker disks, Azure NAT Gateway, Azure worker RBAC, AWS-to-Entra provisioning federation, and cross-cloud placement optimization are excluded from the launch scope. The earlier **Rust Universal Backend plan is superseded by TypeScript/Node.js**, and the earlier **public monorepo assumption is superseded by a private independent `craxii-control-plane` repository**.

We are not building Kubernetes, ECS, dedicated Cloudflare Workers, AWS Lambda, a full microservice network, automatic global/cross-zone fleet replacement, automatic cross-cloud recovery, complex cost-optimized placement, per-customer networks, per-customer custom encryption keys, a dedicated model-inference gateway service, a rich operator dashboard, or advanced model-selection optimization for V0.0.1. **Secure isolation, durable admission and billing, protocol compatibility, recoverable customer data, controlled cloud credentials, and trial abuse prevention are not deferred.** Automatic normal self-service onboarding remains essential.

## 22. Open decisions and external verification gates

The core architecture is settled enough to begin writing the control plane. The remaining **business-policy decisions** are the precise published refund and chargeback rules; the final inactive-data snapshot/archive and reactivation policy for the agreed one-year retention; the active-customer snapshot retention schedule; the exact one-trial-per-person anti-abuse/phone-verification policy; and customer-facing tax, invoices, and deletion-request terms. These cannot be presented as finalized merely because there are engineering recommendations for them.
